### Контекст

У складній прошивці зі значною кількістю коду неминуче виникають труднощі під час його підтримки або додавання нового функціоналу — особливо якщо вся логіка зосереджена в одному або декількох сильно зв'язаних файлах. Інша типова проблема полягає у використанні великої кількості глобальних змінних: кожна з них оголошується один раз і назавжди займає місце в оперативній пам'яті МК, навіть коли вона не задіяна в поточний момент часу.

У **Pixeler** обидві задачі вирішуються розбиттям прошивки на класи контекстів (`IContext`). **Контекст** — це ізольоване середовище (екран або застосунок), в якому виконується користувацький код і яке володіє лише тими ресурсами, що потрібні прямо зараз.

<br>

#### Життєвий цикл контексту

Кожен контекст у Pixeler має власний автоматично керований життєвий цикл.

Після створення об'єкта контексту ядро фреймворку в нескінченному циклі викликає його системний метод `tick()`. Цей метод реалізовано в абстрактному класі `IContext` і він не потребує перевизначення користувачем. Усередині `tick()` виконується така послідовність дій:

1. **Виклик `loop()`:** Через таблицю віртуальних методів викликається метод `loop()` поточного контексту.
   * Якщо `loop()` повертає `false` — поточний цикл для цього контексту завершується до наступного виклику `tick()`.
   * Якщо `loop()` повертає `true` — виконується перевірка таймера кадру, щоб метод `update()` викликався не частіше, ніж це задано в налаштуваннях Pixeler.
2. **Опитування вводу та `update()`:** Коли настає час оновлення кадру, фреймворк зчитує стан користувацького вводу і викликає метод `update()` у класі контексту. Саме в `update()` виконується основна логіка кадру, реакція на кнопки та, якщо активовано GUI, оновлення стану віджетів, створення спливаючих повідомлень (`Toast`) тощо.
3. **Асинхронний вивід на дисплей:** Після завершення `update()` (якщо активовано GUI) сформований кадр передається окремій задачі, яка виводить зображення на дисплей на іншому ядрі процесора, не блокуючи основний потік виконання.

<br>

Найпростіше уявляти кожен клас контексту як окремий файл `main.cpp` у класичному Arduino-проєкті. У ньому є прямі аналоги `setup()` та `loop()`, до яких додається покадровий метод `update()`:

| Етап у контексті | Аналог в Arduino | Коли викликається та для чого використовується |
| :--- | :--- | :--- |
| **Конструктор класу** | `setup()` | Викликається один раз під час створення контексту. Ініціалізація змінних, читання налаштувань із карти пам'яті, побудова початкового макета GUI. |
| **`bool loop()`** | `loop()` | Викликається максимально часто на кожній ітерації головного циклу. Використовується для високопродуктивного коду без затримок (наприклад, заповнення буфера аудіопрогравача). |
| **`void update()`** | — *(новий етап)* | Викликається фіксовану кількість разів на секунду (покадрово). Використовується для перевірки стану кнопок/тачскріна та оновлення елементів інтерфейсу. |
| **Деструктор класу** | — | Викликається автоматично під час переходу до іншого контексту. Звільняє ресурси та відписується від асинхронних подій. |

#### Структура мінімального контексту

Розглянемо приклад контексту головного меню для плати ESP з підключеним дисплеєм та кнопками.

::: {note}
Тут і далі в прикладах використовується допоміжний клас-шаблонізатор `WidgetCreator`, який дозволяє уникати дублювання коду під час створення типових віджетів. Цей клас не є жорсткою частиною ядра фреймворку, проте використання подібного шаблонізатора у вашому проєкті значно спрощує підтримку GUI в єдиному візуальному стилі. Детальніше побудову інтерфейсу розглянуто у розділі [Графічний інтерфейс користувача](gui.md).
:::

##### 1. Ініціалізація в конструкторі (замість `setup`)

```cpp
MenuContext::MenuContext()
{
  // Отримуємо налаштування з карти пам'яті та застосовуємо їх, 
  // встановлюємо початковий стан пінів тощо
  // ...

  // Створюємо за допомогою шаблонізатора новий порожній макет,
  // який буде каркасом для GUI
  EmptyLayout* layout = WidgetCreator::getEmptyLayout();

  // Встановлюємо цей макет для поточного контексту
  setLayout(layout);

  // Створюємо віджет меню з унікальним ідентифікатором,
  // за яким зможемо знайти його на макеті за потреби
  FixedMenu* menu = new FixedMenu(ID_MENU);

  // Додаємо цей віджет до раніше створеного макета
  layout->addWidget(menu);

  // Створюємо новий пункт меню з унікальним ідентифікатором
  MenuItem* files_item = WidgetCreator::getMenuItem(ID_CONTEXT_FILES);

  // Додаємо створений пункт до меню
  menu->addItem(files_item);
}
```

<br>

##### 2. Покадрова логіка в методі `update()`

У методі `update()`, який викликається автоматично кожен кадр, обробляємо користувацький ввід та керуємо інтерфейсом:

```cpp
void MenuContext::update()
{
  // Обробляємо стан кнопок
  if (_input.isHolded(BtnID::BTN_UP))
  {
    up();
  }
  else if (_input.isReleased(BtnID::BTN_BACK))
  {
    // Якщо відпущено кнопку "Назад", даємо команду Pixeler
    // звільнити поточний контекст і завантажити HomeContext
    openContext(new HomeContext());
  }
  // Далі обробляємо натискання інших кнопок, якщо потрібно
  // ...
}

void MenuContext::up()
{
  // Переміщуємо фокус на попередній елемент меню
  _menu->focusUp();
}

void MenuContext::down()
{
  // Переміщуємо фокус на наступний елемент меню
  _menu->focusDown();
}
```

<br>

##### 3. Швидкий цикл у методі `loop()`

У методі `loop()` виконується високопродуктивний код, який потребує максимальної частоти викликів:

```cpp
bool MenuContext::loop()
{
  // Тут виконується робота, яка не повинна перериватися 
  // тривалими затримками між кадрами (наприклад, декодування аудіопотоку)
  // ...

  return true;
}
```

Метод `loop()` обов'язково повертає булеве значення, яке повідомляє батьківському `IContext`, чи потрібно в поточному контексті зчитувати стан вводу та викликати `update()`:
* **`true`** повинен повертати лише активний (та найбільш глибоко вкладений) контекст. Це запобігає повторному зчитуванню стану кнопок для кожного вкладеного контексту в межах одного кадру.
* **`false`** означає, що контекст пропускає зчитування вводу, виклик `update()` та формування зображення для дисплея. Завдяки цьому майже весь процесорний час отримує саме активний контекст.

Кожен клас контексту обов'язково повинен реалізувати **конструктор**, **деструктор**, а також методи **`loop()`** та **`update()`**. Уся інша логіка та допоміжні методи додаються на розсуд розробника.

<br>

#### Перемикання контексту

Для зміни поточного контексту в Pixeler використовуються два методи:

```cpp
/**
 * @brief Позначає поточний контекст для звільнення на наступному тіку
 * та встановлює новий об'єкт контексту, у який буде виконано перехід.
 *
 * @param context Вказівник на новий об'єкт контексту (створений через оператор new) або nullptr.
 * Передача nullptr із субконтексту означає вихід із вкладеного режиму до батьківського контексту.
 * Передача nullptr у контексті першого рівня призведе до перезавантаження прошивки.
 */
void openContext(IContext* context);

/**
 * @brief Позначає поточний вкладений субконтекст для звільнення на наступному тіку.
 * Виклик цього методу в контексті першого рівня призведе до перезавантаження прошивки.
 */
void releaseContext();
```

<br>

* **`openContext(IContext* context)`** — основний спосіб переходу між екранами прошивки. У метод передається вказівник на створений через `new` об'єкт класу, успадкованого від `IContext`. Поточний контекст буде автоматично видалено з пам'яті, а його місце займе новий:
  ```cpp
  openContext(new YourNextContext());
  ```
* **`releaseContext()`** — викликається **ТІЛЬКИ у субконтексті** (тобто у класі контексту, який вкладено всередину іншого батьківського контексту). У більшості звичайних екранів у ньому немає потреби. Типовий приклад використання можна побачити у прошивці до плати *Perfect Devboard*, де `LuaContext` запускається як дочірній субконтекст усередині контексту файлового менеджера і після завершення скрипта повертає керування назад через `releaseContext()`.
