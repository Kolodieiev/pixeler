### Ігровий об'єкт (`IGameObject2D`)

Абстрактний клас **`IGameObject2D`** (`#include "game/2D/IGameObject2D.h"`) є єдиною сутністю ігрового рушія, яка може містити власну ігрову логіку на сцені. Ігровим об'єктом є все (від головного героя, ворогів та каменів до невидимих зон-тригерів або вільної камери), окрім плиток рельєфу.

Рушій Pixeler є жанрово-універсальним (підходить як для ігор із виглядом зверху *top-down*, так і для вигляду збоку *side-view*), тому він не нав'язує важкої фізичної симуляції (гравітації, інерції чи прискорення). Натомість кожен об'єкт оперує чотирма базовими механізмами:
1. **Спрайт та його стани (`SpriteState`, `SpriteTemplate`)** — статичні зображення або покадрові анімації.
2. **Геометрія та зміщення твердого тіла (`SpriteGeometry`, `RigidOffsets`)** — габарити об'єкта та налаштування хітбоксу відносно країв картинки.
3. **Прохідність та колізії (`PhysicsState`)** — прапор твердого тіла та бітова маска дозволених типів плиток терейну.
4. **Серіалізація (`DataStream`)** — пакування та розпакування власного стану у потік байтів для збережень гри, переходів між рівнями або синхронізації по мережі.

<br>

#### Особливості архітектури: Пряма взаємодія та `type_ID`

Програмуючи ігри під мікроконтролер, необхідно постійно зважати на обмежені ресурси процесора та пам'яті:
* **Власна система ідентифікаторів типів (`type_ID`):** Задля економії оперативної та Flash-пам'яті прошивка для ESP32 компілюється з вимкненим механізмом C++ RTTI (`type_info`). Тому для розпізнавання типів об'єктів на сцені розробник створює власне перелічення (наприклад, `enum ObjType : uint16_t { TYPE_HERO, TYPE_BOX, TYPE_PORTAL }`) і передає відповідний ідентифікатор у конструктор базового класу `IGameObject2D`.
* **Прямий доступ без посередників:** З точки зору класичного геймдеву для ПК об'єкти не повинні звертатися один до одного або до сцени напряму. Проте на мікроконтролері додаткові прошарки абстракції та копіювання даних на кожному кадрі помножаться на кількість об'єктів і з'їдять дорогоцінні мілісекунди ядра (FPS). Тому в Pixeler об'єкти мають прямий доступ до методів сцени `_scene`, а їхні глобальні координати (`_x_global`, `_y_global`) є відкритими для читання та зміни іншими об'єктами без необхідності приведення типів. Контроль за тим, щоб об'єкт реагував лише на цілі в межах свого радіуса дії, покладається на логіку в коді самого об'єкта (а у мультиплеєрі — на валідацію сервером).

#### 1. Геометрія спрайта та зміщення твердого тіла (`RigidOffsets`)

Хоча фізика імпульсів у рушії не використовується, кожен об'єкт за замовчуванням має прямокутне **тверде тіло (хітбокс)**, яке спочатку дорівнює розміру його спрайта. Проте у більшості 2D-ігор видиме зображення спрайта не повинно на 100% збігатися з його фізичним тілом:
* **Ілюзія глибини та вертикальності (Top-Down):** Коли персонаж підходить знизу впритул до стіни будинку або іншого твердого об'єкта, його голова та плечі мають візуально перекривати нижній край стіни, а колізія має рахуватися лише по ногах/нижній частині тулуба.
* **Виступаючі частини тіла чи зброї:** Голова коня або зброя в руках персонажа можуть візуально нависати над плиткою води, доки ноги персонажа стоять на твердій землі.
* **Динамічні перешкоди та фільтрація:** Об'єкт каменю з твердим тілом може блокувати вузький прохід на карті, доки гравець не виконає умову для його знищення, а просторові методи пошуку об'єктів можуть фільтрувати влучання саме по хітбоксу твердого тіла.

Для налаштування хітбоксу в структурі **`SpriteGeometry`** використовуються відступи твердого тіла **`RigidOffsets`** (відступи всередину від верхнього, нижнього, лівого та правого країв спрайта):

```cpp
struct SpriteGeometry
{
  RigidOffsets rigid_offsets{}; // Відступи твердого тіла від країв спрайта (top, bottom, left, right)
  uint16_t width{1};            // Загальна ширина зображення спрайта
  uint16_t height{1};           // Загальна висота зображення спрайта
  uint16_t x_pivot{1};          // X-координата логічного центру (опорної точки) спрайта
  uint16_t y_pivot{1};          // Y-координата логічного центру (опорної точки) спрайта
};
```

Один і той самий тип об'єкта у своєму шаблоні **`SpriteTemplate`** може мати декілька варіантів зображень (`img_variants`), анімацій (`animation_variants`) та геометрій (`geometry_variants`) — наприклад, коли довгий об'єкт (кінь або човен) повертається з горизонтального положення у вертикальне.

Перемикання між зареєстрованими варіантами виконується в коді об'єкта за їхнім порядковим індексом (`0, 1, ...`):

```cpp
setImgVariant(0);       // Встановити варіант статичного зображення №0
setAnimationVariant(1); // Встановити варіант вектора анімації №1
setGeometryVariant(0);  // Встановити варіант геометрії та хітбоксу №0
```

::: {warning}
**Важливі правила роботи з геометрією та `RigidOffsets`:**
1. **Контроль розмірів:** Розробник повинен самостійно стежити, щоб сума лівого і правого відступів (`left + right`) не перевищила ширину спрайта `width`, а сума верхнього і нижнього (`top + bottom`) — висоту `height`.
2. **Ручне перемикання геометрії при зміні ракурсу:** Якщо форма твердого тіла має змінюватися разом із напрямком руху чи анімацією (наприклад, розворот вершника на 90°), розробник повинен самостійно викликати `setGeometryVariant(...)` під час зміни анімації.
3. **Перевірка індексів:** Звернення у `setImgVariant()`, `setAnimationVariant()` або `setGeometryVariant()` до індексу, який не був попередньо доданий у `SpriteTemplate` при реєстрації на сцені, викличе аварійне перезавантаження МК.
:::

#### 2. Керування станом спрайта, анімацією (`_sprite`) та шаром (`_layer`)

Анімування об'єктів у Pixeler працює за принципом GIF-ефекту: рушій автоматично перемикає кадри із заданого вектора зображень через кожні `frames_between_anim` кадрів сцени. Усі окремі кадри анімації, як і статичні зображення одного варіанту геометрії, повинні мати однаковий розмір.

Оскільки напівпрозоре змішування кольорів із альфа-каналом є занадто важкою операцією для мікроконтролера, у спрайтах використовується колір-ключ, який рушій розпізнає як повністю прозорий (`COLOR_TRANSPARENT`). Самі масиви зображень для спрайтів та кадрів анімації конвертуються у 16-бітний формат RGB565 точно так само, як і плитки терейну.

Усередині класу об'єкта поточний візуальний стан керується через структуру **`_sprite` (`SpriteState`)**:

| Поле `_sprite` | Тип | Призначення |
| :--- | :--- | :--- |
| **`has_img`** | `bool` | Якщо `true` — об'єкт відмальовує статичне зображення, обране через `setImgVariant()`. |
| **`has_animation`** | `bool` | Якщо `true` — об'єкт програє покадрову анімацію, обрану через `setAnimationVariant()`. |
| **`frames_between_anim`** | `uint8_t` | Кількість кадрів сцени, які пропускаються перед перемиканням на наступний кадр анімації (регулює швидкість анімації). |
| **`angle`** | `int16_t` | Кут повороту спрайта в градусах (за замовчуванням `0`). |

* **Синхронізація станів анімації:** У рушії немає жорсткої прив'язки анімацій до подій — розробник сам вирішує (у методах руху або в `__update()`), коли перемкнути вектор анімації через `setAnimationVariant()`, коли скинути її на перший кадр викликом **`_sprite.resetAnimation()`**, або коли вимкнути `has_animation = false` і перейти на статичний кадр спокою (`has_img = true`).
* **Порядок накладання (`_layer`):** Глибина об'єкта по осі Z регулюється полем **`_layer`** (`uint8_t`, за замовчуванням `0`). Чим більше значення `_layer`, тим вище малюється об'єкт. У межах одного значення `_layer` сцена автоматично сортує об'єкти по осі Y (об'єкти з більшою координатою Y перекривають об'єкти, що стоять вище на карті).

::: {note}
**Керування пам'яттю зображень спрайта:** Ігровий об'єкт **не видаляє** дані зображень за вказівниками під час свого знищення. Це зроблено навмисно, щоб десятки об'єктів могли безпечно перевикористовувати один і той самий графічний ресурс. Якщо текстури спрайтів завантажувалися динамічно з SD-карти в оперативну пам'ять (наприклад, через `_res`), звільнити їх має той об'єкт (сцена або контекст), який їх завантажив.
:::

#### 3. Тверде тіло, маска прохідності (`_physics`) та переміщення

Властивості фізичної взаємодії об'єкта з поверхнею сцени та іншими об'єктами задаються в полі **`_physics` (`PhysicsState`)**:

```cpp
// 1. Вмикаємо тверде тіло (інші об'єкти не зможуть проходити крізь цей об'єкт)
_physics.is_rigid = true;

// 2. Задаємо бітову маску плиток терейну, якими об'єкту дозволено пересуватися
_physics.pass_ability_mask = TILE_TYPE_GROUND | TILE_TYPE_ROAD;
```

Коли ви викликаєте метод сцени **`_scene.canPass(*this, x_to, y_to)`**, рушій автоматично бере габарити поточного об'єкта з урахуванням його `rigid_offsets` і перевіряє:
1. Чи не виходить об'єкт за межі карти рівня.
2. Якщо **`_physics.is_rigid == true`**: чи всі плитки терейну під майбутнім хітбоксом об'єкта входять до його маски `_physics.pass_ability_mask`, і чи немає в цільовій точці іншого об'єкта з увімкненим твердим тілом.
3. Якщо **`_physics.is_rigid == false`** (тверде тіло вимкнено): об'єкт ігнорує типи прохідності плиток та інші об'єкти й може вільно переміщуватися по всій поверхні рівня (обмежуючись лише зовнішніми краями карти).

::: {warning}
**Застереження щодо кроку переміщення (ефект тунелювання):**
Під час виклику `_scene.canPass(*this, x_to, y_to)` перевіряється лише кінцева область, куди об'єкт планує стати. Якщо крок переміщення об'єкта за один кадр **перевищує розмір однієї плитки терейну**, рушій не перевірятиме типи проміжних плиток між поточною та кінцевою точками (об'єкт зможе «перестрибнути» тонку стіну). Тому крок руху за один кадр для твердих тіл має бути меншим за ширину плитки.
:::

#### 4. Життєвий цикл та приклади реалізації об'єкта

Кожен клас, успадкований від `IGameObject2D`, обов'язково повинен реалізувати:
* Конструктор зі стандартною сигнатурою `(uint32_t id, IGameScene2D& game_scene, SfxPlayer& audio)`, який викликає базовий конструктор `IGameObject2D(id, TYPE_ID, game_scene, audio)`.
* Метод покадрового оновлення **`void __update() override`** (викликається сценою автоматично на кожному кадрі; для пасивних об'єктів може залишатися порожнім, а для автономних ботів/снарядів тут описується пошук цілей, переслідування чи атака).
* Три методи серіалізації: **`getDataSize()`**, **`serialize(DataStream& ds)`** та **`deserialize(DataStream& ds)`**.

За потреби ви також можете перевизначити віртуальний метод **`void __onDraw() override`**, щоб домалювати поверх або навколо об'єкта додаткову графіку (наприклад, індикатор міцності чи смужку здоров'я над головою), обов'язково викликавши всередині базовий `IGameObject2D::__onDraw()`.

##### Приклад реалізації ігрового об'єкта (`SokobanObj`)

```cpp
namespace sokoban
{
  SokobanObj::SokobanObj(uint32_t id, IGameScene2D& game_scene, SfxPlayer& audio)
      : IGameObject2D(id, TYPE_HERO, game_scene, audio)
  {
    _layer = 1;                     // Малювати поверх об'єктів точок (які на шарі 0)
    _sprite.has_img = true;         // Дозволити вивід статичного спрайта
    setImgVariant(0);               // Обрати перше зображення з шаблону TYPE_HERO
    setGeometryVariant(0);          // Обрати базову геометрію 32x32
    _physics.pass_ability_mask |= TILE_TYPE_GROUND; // Дозволити рух тільки по підлозі
    _physics.is_rigid = true;       // Увімкнути тверде тіло
  }

  void SokobanObj::__update()
  {
    // Перевіряємо умову перемоги на кожному кадрі: чи всі ящики на своїх місцях
    bool done{true};
    for (uint8_t i{0}; i < _boxes.size(); ++i)
    {
      if (!_boxes[i]->isOk())
      {
        done = false;
        break;
      }
    }

    // Якщо всі ящики встановлено — активуємо тригер переходу на наступний рівень
    if (done)
    {
      _trigger_ID = TriggerID::TRIGGER_NEXT_SCENE;
      _is_triggered = true;
    }
  }

  void SokobanObj::__onDraw()
  {
    // Необов'язковий метод: тут можна домалювати рамку виділення або смужку здоров'я (HP)
    
    // Обов'язковий виклик батьківського методу для виводу самого спрайта або анімації:
    IGameObject2D::__onDraw();
  }

  void SokobanObj::stepTo(uint16_t x, uint16_t y, uint16_t box_x_step, uint16_t box_y_step)
  {
    const std::array types = {(uint16_t)TYPE_BOX};

    // 1. Шукаємо, чи є ящик у клітинці попереду за напрямком руху
    std::vector<IGameObject2D*> objs = _scene.getObjByTypeAt(types, x, y, this);

    if (!objs.empty())
    {
      BoxObj* box = static_cast<BoxObj*>(objs[0]);
      if (box->moveTo(box_x_step, box_y_step)) // Намагаємося штовхнути ящик далі
      {
        _x_global = x; // Якщо ящик посунувся — стаємо на його місце
        _y_global = y;
      }
      return;
    }

    // 2. Якщо ящика попереду немає — перевіряємо прохідність через сцену
    if (_scene.canPass(*this, x, y))
    {
      _x_global = x;
      _y_global = y;
    }
  }
} // namespace sokoban
```

#### 5. Допоміжні геометричні та просторові методи `IGameObject2D`

Усередині методів вашого об'єкта доступні вбудовані математичні функції для перевірки перетинів, розрахунку відстаней та руху до цілі:

| Метод об'єкта | Опис |
| :--- | :--- |
| **`setPos(x, y)`**, **`getGlobalX()`**, **`getGlobalY()`** | Встановлення та отримання глобальних координат об'єкта на карті рівня. |
| **`hasIntersectWithPoint(x, y, [rigid_only])`** | Перевіряє, чи перетинається об'єкт із точкою `(x, y)`. Якщо `rigid_only = true` — перевіряє лише хітбокс твердого тіла, інакше — весь прямокутник спрайта. |
| **`hasIntersectWithCircle(x, y, r, [rigid_only])`** | Перевіряє перетин об'єкта з колом радіуса `r`. |
| **`hasIntersectWithRect(x, y, w, h, [rigid_only])`** | Перевіряє перетин об'єкта із заданим прямокутником. |
| **`calcAngleToPoint(x, y)`** | Обчислює кут (у градусах) від опорної точки (`pivot`) об'єкта до точки `(x, y)`. |
| **`calcDistToPoint(x, y)`** | Обчислює відстань у пікселях від `pivot` об'єкта до точки `(x, y)`. |
| **`stepToPoint(x_to, y_to, step_w)`** | Зміщує об'єкт по прямій лінії у напрямку точки `(x_to, y_to)` на крок `step_w` пікселів (зручно для руху снарядів або переслідування гравця ботами). |

#### 6. Серіалізація та збереження стану об'єктів (`DataStream`)

У Pixeler реалізовано вбудований механізм бінарної серіалізації ігрових об'єктів за допомогою класу потоку байтів **`DataStream`**. Він використовується для збереження гри у файл на SD-карті, перенесення об'єктів між ігровими рівнями (через буфер `_stored_objs` у контексті) та синхронізації стану по мережі.

##### Як працює збереження сцени (Серіалізація)
1. Сцена викликає метод **`calcObjectsSize()`**, який опитує всі активні об'єкти через їхній метод **`getDataSize()`** і підраховує сумарний обсяг байтів, необхідний для збереження. (Якщо об'єкт не потребує збереження свого стану, його `getDataSize()` просто повертає `0`).
2. Створюється буфер `DataStream` відповідного розміру і передається у метод сцени **`serializeObjects(DataStream& ds)`**.
3. Сцена по черзі записує у потік ідентифікатор типу об'єкта (`_type_ID`) та викликає на об'єкті віртуальний метод **`serialize(ds)`**, у якому об'єкт сам записує у потік свої поля (координати, здоров'я, інвентар тощо).
4. Сформований потік байтів `DataStream` записується у файл збереження на SD-карті через файловий менеджер `_fs`.

##### Як працює відновлення зі збереження (Десеріалізація)
Процес завантаження працює у зворотному порядку:
1. Контекст гри (або меню сцени) зчитує бінарний файл збереження з SD-карти у потік `DataStream` і передає його сцені.
2. Сцена у циклі вичитує з потоку черговий ідентифікатор типу об'єкта (`type_ID`), створює відповідний екземпляр через `createObject<T>()` і передає йому потік у метод **`deserialize(ds)`**.
3. Об'єкт вичитує з потоку свої поля **строго в тому самому порядку, у якому вони записувалися в `serialize()`**, відновлює свій стан і додається на сцену, після чого цикл переходить до читання наступного об'єкта, доки потік не буде вичитано до кінця.
