### Асинхронність

Для забезпечення асинхронності та підтримки багатопотоковості в Pixeler використовується механізм `post`-повідомлень. 

Будь-який зворотний виклик (`callback`) у класі контексту або ігрової сцени, в результаті якого відбувається зміна або оновлення графічного інтерфейсу (GUI), обов'язково повинен передати до цього об'єкта лямбду за допомогою методу `post()`. Цю задачу буде додано до потокобезпечної черги та безпечно опрацьовано в потоці UI під час наступного виклику `tick()` контексту або `update()` ігрової сцени.

```cpp
/**
 * @brief Додає функцію до черги, яку буде опрацьовано
 * в потоці контексту під час наступного виклику tick().
 * Може викликатись з будь-якої FreeRTOS-задачі.
 *
 * @param task Функція без аргументів та повернення результату,
 * яка повинна бути виконана в потоці UI
 * @param timeout_ms Максимальний час очікування (у мілісекундах) вільного місця в черзі,
 * за замовчуванням — неблокуючий виклик
 * @return true — якщо функцію успішно додано в чергу. 
 * @return false — якщо черга переповнена і час очікування вичерпано.
 */
bool post(std::function<void()> task, unsigned long timeout_ms = 0);

// Приклад використання в асинхронному мережевому обробнику:
void ServerChessContext::onAcceptHandler(const String client_name, void* arg)
{
    ServerChessContext* self = static_cast<ServerChessContext*>(arg);
    self->post([self, client_name]()
            { self->showClientAcceptTmpl(client_name); }, 500);
}
```

<br>

::: {warning}
**Важливо:** Будь-який інший прямий спосіб зміни елементів GUI з паралельних задач FreeRTOS (поза межами черги `post`) **не є безпечним** і може призвести до збою прошивки через конкурентний доступ до пам'яті (`race condition`) або пошкодження буфера відмальовування.
:::
